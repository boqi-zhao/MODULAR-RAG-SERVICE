# 测试先行与评审流程

状态：开发方式已确认采用 TDD；当前仅记录流程，不预先确定各 Stage 的字段或详细用例。
首批 PDF 解析已完成评审、失败测试与实现，见 [测试记录](reviews/pdf-parse/09-test-results.md)；后续范围仍分批设计、评审。

## 开发顺序

1. 明确本次要开发的模块或子阶段及需求边界。
2. 在文档中设计用例，描述输入条件、操作、预期输出及必要的失败场景。
3. 与用户评审用例及相关输入输出；未确认字段和行为保留待定，不能开始开发。
4. 用户明确评审通过后，先写测试并运行，确认预期失败（Red）。
5. 实现本次范围的代码，使测试通过（Green）。
6. 在测试保持通过的前提下重构，运行相关 pytest 与 Ruff 检查。

文档写完不等于评审通过；某组用例通过不代表其他阶段或全部业务已获开发授权。
输入输出在对应阶段评审时确定，不提前生成所有阶段的 schema、类型或实现。

## 执行约定

- 用例与测试可追溯，记录评审结论和必要修改，不维护无实际用途的字段清单。
- 需求变更影响已评审行为时，先更新用例并重新确认受影响范围。
- 单元、集成和端到端测试按实际风险选择，不为内部实现写镜像测试。
- PostgreSQL 锁与并发行为用真实 PostgreSQL 验证；mock 不能替代真实组件或端到端验收。
- 10 用户验收与内部文档处理并发分开，要求见 [并发设计](04-concurrency.md)。
- 当前仅规划实现 PDF；Markdown/QA CSV 扩展边界保留，相关实现与用例留待后续范围。
- 测试和实现均遵守项目的单次代码写入行数及说明性注释要求。

不以先实现后补测试替代 TDD，不以跳过测试或空测试套件宣称验证通过。
