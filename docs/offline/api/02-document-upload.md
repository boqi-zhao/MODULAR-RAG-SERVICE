# 第二步：上传 PDF，保存原文件

状态：本地保存与多文件接口（`files` 字段、逐份结果、限额）已实现、验证及用户评审通过。
已完成 [PG 接入](04-postgresql-connection.md)、[上传记录读写](03-upload-records.md) 与本地文件保存、`POST /documents` 接口；本步不启动解析。

## 本步做什么

一次请求接收多份 PDF（默认最多 10 份），每份完整保存原始字节、单独登记上传记录，再返回逐份结果。
每份独立处理：某份失败不回滚其他已成功的文件或记录；全部失败时返回 HTTP 400。
本步不启动解析任务。
后续解析接口根据文档编号读取已保存的文件，再提交后台任务。
上传成功表示该份原文件和数据库记录都已保存，不表示 PDF 已能解析。

## 建议的接口

| 项目 | 建议 |
| --- | --- |
| 地址 | `POST /documents`，先用通用文档名称，为后续 Markdown、CSV 留扩展位置 |
| 上传方式 | Postman 的 Body 选择 form-data，字段名 `files`，可添加多行，每行一个文件 |
| 单次范围 | 一次最多 10 份（`UPLOAD_MAX_FILES`）；超过份数整单拒绝 |
| 文件限制 | 每份最多 20 MiB（`UPLOAD_MAX_BYTES`）；单次总大小最多 100 MiB（`UPLOAD_MAX_TOTAL_BYTES`） |
| 初步检查 | 每份：非空、文件名以 `.pdf` 结尾、前 1024 字节包含 PDF 文件头 `%PDF-` |
| 完整检查 | 文件是否损坏、是否加密、扫描风险等，由后续解析阶段检查 |
| 成功响应 | HTTP 201；至少一份完成“文件保存 + PG 记录提交” |
| 全部失败 | HTTP 400，逐份列出失败原因；混有成功时仍返回 201，在 body 标出失败项 |

建议的响应示例；这些字段只描述文件接入，不固定 parse 的返回结构：

```json
{
  "succeeded": 1,
  "failed": 1,
  "documents": [
    {
      "filename": "example.pdf",
      "status": "uploaded",
      "document_id": "doc_<UUID>",
      "source_format": "pdf",
      "size_bytes": 12345,
      "sha256": "<原始文件字节的 SHA-256>"
    },
    {
      "filename": "note.txt",
      "status": "failed",
      "error": "首批只接收 PDF 文件，文件名需以 .pdf 结尾。"
    }
  ]
}
```

`documents` 顺序与请求中 `files` 的顺序一致；失败项只返回文件名和原因，不返回文档编号。文件已保存但 PG 更新失败时保留文件供排查，见上传记录说明。
`document_id` 是服务分配的文档编号，SHA-256 是内容校验和，两者分开；每份文件各自分配新编号。
每次上传分配新编号，不按同名文件或相同内容自动覆盖旧文档；一份失败不影响其他成功项。
本步不支持更新已有文档；文档版本和批次规则后续确定。

## 本地怎么保存

- 默认根目录建议为 `data/uploads/`，通过服务配置指定；运行文件不提交 Git。
- 每份文档用独立编号目录，仅保存 `source.pdf`；原文件名等信息写入 PG，不再重复保存 `metadata.json`。
- 接收完成后先检查份数和各文件大小之和，超限时整单拒绝、不写任何文件。
- 上传按固定大小分段读取和写入，同时计算大小与 SHA-256，避免把完整文件读入内存。
- 写入临时目录，全部完成后再发布；目标已存在时拒绝覆盖，大小超限或写入失败时清理本次临时文件。
- 每次调用使用独立临时文件，同编号并发时各自写入、互不影响，且只清理自己创建的临时文件。
- 上传记录由 PostgreSQL 持久保存；记录内容和失败处理见 [上传记录](03-upload-records.md)。
- 本步会接入 PG 上传记录；解析任务、调度和进度继续留在后续步骤。
- 不把本地绝对路径作为响应字段；后续业务按文档编号访问原文件。

## 失败行为与验证

| 情况 | 响应与检查点 |
| --- | --- |
| 缺少 `files` | 422，不产生任何上传 |
| 份数超过限制 | 413，整单拒绝，不写盘 |
| 单次总大小超过限制 | 413，整单拒绝，不写盘 |
| 某份为空 | 该份失败（“文件内容为空”）并标 failed，其他继续 |
| 某份格式初步检查不通过 | 该份失败（只接收 PDF），其他继续 |
| 某份超过单份大小限制 | 该份失败，清理该份未完成文件，其他继续 |
| 某份存储失败 | 该份失败，不返回上传成功，不泄露服务器路径 |
| 数据库不可用 | 建记录失败的文件都标 failed；全部因此失败时返回 503 |

验证真实 PDF 上传后，保存字节与输入一致，PG 有对应记录；再次上传不会覆盖第一次。
一份请求多份时，成功与失败混合也要分别核对：成功的文件和记录保留，失败的不留正式文件。
失败记录或未完成记录不能用于提交解析；文件与数据库的异常情况见 [上传记录](03-upload-records.md)。
上传路由 `src/api/documents.py` 只接收请求、转换输入和返回 HTTP 响应。
`src/uploads/service.py` 负责批次限制、逐份处理、调用文件保存和记录读写、统计结果；不依赖 FastAPI。
service 接收 `UploadInput`（文件名、文件流、大小），返回 `UploadBatchResult`；整批超限抛出业务异常，由路由映射为 413。
`src/uploads/files.py` 负责本地文件保存，`src/db/upload_records.py` 负责数据库读写。

## 上传结果模型

Pydantic 已列为直接依赖；模型在 `src/uploads/schemas.py`，不依赖 FastAPI。
- `UploadSucceeded`：成功必须有文档编号、正数大小、64 位 SHA-256；状态固定为 `uploaded`。
- `UploadFailed`：失败必须有原因，状态固定为 `failed`，不允许混入成功字段。
- `UploadResponse`：批次成功数、失败数与逐份结果；按 `status` 区分成功和失败模型。

模型拒绝多余字段和隐式类型转换；service 创建结果时即校验，路由使用 `response_model` 校验响应并生成接口文档。
上传仍用 multipart 的 `files` 字段；文件流输入保留 `UploadInput`，不转换为 JSON 模型。
原 HTTP 状态码和 JSON 字段保持一致；`/docs` 已展示 201、400、503 的明确响应结构。
