# 第二步：上传 PDF，保存原文件

状态：本文件接口与保存行为已评审通过；原文件保存本地，上传记录写入 PostgreSQL。
已完成 [PG 接入](04-postgresql-connection.md) 与 [上传记录读写](03-upload-records.md)；本地文件保存和上传接口尚未实现。

## 本步做什么

接收一份 PDF，完整保存原始字节，在 PostgreSQL 中登记上传记录，再返回上传凭据。
本步不启动解析任务。
后续解析接口根据文档编号读取已保存的文件，再提交后台任务。
上传成功表示原文件和数据库记录都已保存，不表示 PDF 已能解析。

## 建议的接口

| 项目 | 建议 |
| --- | --- |
| 地址 | `POST /documents`，先用通用文档名称，为后续 Markdown、CSV 留扩展位置 |
| 上传方式 | Postman 的 Body 选择 form-data，字段名 `file`，类型选 File |
| 单次范围 | 一份 PDF；用户选择多份文档时可多次上传，批次提交后续另做 |
| 文件限制 | 首批建议最多 20 MiB（20 × 1024 × 1024 字节），由服务配置控制 |
| 初步检查 | 非空、文件名以 `.pdf` 结尾、前 1024 字节包含 PDF 文件头 `%PDF-` |
| 完整检查 | 文件是否损坏、是否加密、扫描风险等，由后续解析阶段检查 |
| 成功响应 | HTTP 201；原文件保存完成、PG 上传记录提交成功后才返回 |

建议的响应示例；这些字段只描述文件接入，不固定 parse 的返回结构：

```json
{
  "document_id": "doc_<UUID>",
  "status": "uploaded",
  "filename": "example.pdf",
  "source_format": "pdf",
  "size_bytes": 12345,
  "sha256": "<原始文件字节的 SHA-256>"
}
```

`document_id` 是服务分配的文档编号，SHA-256 是内容校验和，两者分开。
每次上传分配新编号，不按同名文件或相同内容自动覆盖旧文档。
本步不支持更新已有文档；文档版本和批次规则后续确定。

## 本地怎么保存

- 默认根目录建议为 `data/uploads/`，通过服务配置指定；运行文件不提交 Git。
- 每份文档用独立编号目录，仅保存 `source.pdf`；原文件名等信息写入 PG，不再重复保存 `metadata.json`。
- 上传按固定大小分段读取和写入，同时计算大小与 SHA-256，避免把完整文件读入内存。
- 写入临时目录，全部完成后再发布；大小超限或写入失败时清理本次临时文件。
- 上传记录由 PostgreSQL 持久保存；记录内容和失败处理见 [上传记录](03-upload-records.md)。
- 本步会接入 PG 上传记录；解析任务、调度和进度继续留在后续步骤。
- 不把本地绝对路径作为响应字段；后续业务按文档编号访问原文件。

## 失败行为与验证

| 情况 | HTTP 响应与检查点 |
| --- | --- |
| 缺少 `file` | 422，不产生已完成的上传 |
| 空文件 | 400，说明文件为空 |
| 格式初步检查不通过 | 415，说明首批只接收 PDF |
| 超过大小限制 | 413，清理本次未完成文件 |
| 存储失败 | 500，不返回上传成功，不泄露服务器路径 |
| 数据库不可用 | 503，不返回上传成功 |

验证真实 PDF 上传后，保存字节与输入一致，PG 有对应记录；再次上传不会覆盖第一次。
失败记录或未完成记录不能用于提交解析；文件与数据库的异常情况见 [上传记录](03-upload-records.md)。
上传路由负责接收和响应，本地保存逻辑放在独立模块；分文件后逐段讲解，并补充 Postman 请求。
