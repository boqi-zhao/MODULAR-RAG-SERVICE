# 上传记录表设计

状态：表结构设计已评审通过；ORM 模型与首次 Alembic 迁移已实现并验证，等待本步代码评审；记录读写尚未实现。
沿用已通过的 [上传记录方案](03-upload-records.md)，一条记录代表一次上传。

## 表名与字段

建议表名：`public.document_uploads`。PDF 字节仍保存在本地，不放进数据库。
“可为空”表示信息尚未得到时保存 `NULL`，不使用空字符串或数字 0 冒充未知值。

| 字段 | PG 类型 | 可为空 | 含义与规则 |
| --- | --- | --- | --- |
| `document_id` | `text` | 否 | 文档编号，主键；服务生成 `doc_` 加带短横线的小写 UUID v4 |
| `filename` | `text` | 否 | 原文件名，非空；只用于展示，不用于拼接保存路径 |
| `source_format` | `text` | 否 | 来源格式，非空；当前服务只写 `pdf` |
| `size_bytes` | `bigint` | 是 | 完整接收的文件字节数；已知时不得为负，上传成功时必须大于 0 |
| `sha256` | `text` | 是 | 完整原文件的校验和；已知时必须为 64 位小写十六进制字符 |
| `storage_type` | `text` | 否 | 存储类型，非空；当前服务只写 `local` |
| `storage_key` | `text` | 否 | 正式文件的相对路径，如 `doc_<UUID>/source.pdf`；非空 |
| `status` | `text` | 否 | 仅允许 `uploading`、`uploaded`、`failed`；初始值为 `uploading` |
| `created_at` | `timestamptz` | 否 | 开始时间，由数据库默认填写当前时间 |
| `completed_at` | `timestamptz` | 是 | 上传成功或失败的结束时间；接收中为空 |
| `error_message` | `text` | 是 | 失败说明，如“文件超过大小限制”；不保存密码、绝对路径或完整底层异常 |

`text` 保存文字；`bigint` 保存整数；`timestamptz` 保存明确的时间点，应用按 UTC 输出。
文档编号带 `doc_` 前缀，因此整串用 `text` 保存；生成格式由服务校验，数据库主键保证不重复。
`storage_key` 相对于上传根目录，不包含 `data/uploads/` 或本机绝对路径。
编号及正式路径在开始时就能确定；文件是否已保存，要看状态，不能仅看路径字段是否存在。
文件大小上限由服务配置控制，不把当前的 20 MiB 写死在数据库约束中。

## 数据库必须拦住哪些错误

下列规则通过数据库约束实现；不满足规则时，数据库拒绝写入。

| 状态 | 必须满足 |
| --- | --- |
| `uploading` | `completed_at`、`error_message` 必须为空；大小和校验和可以为空 |
| `uploaded` | 大小必须大于 0，校验和及结束时间必须有值，失败说明必须为空 |
| `failed` | 结束时间和非空失败说明必须有值；大小、校验和可以为空 |

- 已填写的结束时间不得早于开始时间；完成时间由数据库填写，避免混用客户端时钟。
- 文件名、格式、存储类型、存储键不得为空字符串或仅含空白。
  空白按 Unicode 空白字符判断：除空格和常见换行外，竖向制表符、换页符、不换行空格、全角空格等也不能单独构成有效文本。
- `(storage_type, storage_key)` 组合不允许重复，避免两条记录指向同一个正式文件位置。
- SHA-256 不设唯一约束；同名或相同内容重复上传，仍各有编号、文件和记录。
- 数据库只能检查记录本身，不能证明本地文件存在或字节完整；上传模块仍须实际核对。

格式和存储类型使用文字字段，当前只接入 PDF 和本地存储。
后续接入 Markdown、QA CSV 或存储桶时，再确定新增取值及存储键规则；本步不实现这些格式。
主键和存储位置的唯一约束会建立索引，索引用于加快查找并防止重复。
暂不增加其他索引；上传列表、异常恢复有实际查询需求后，再按查询条件补充。

## 状态如何变化，以及并发如何处理

正常流程：`uploading → uploaded`；接收、校验或保存失败：`uploading → failed`。
成功和失败都是本次上传的结束；用户重新上传会生成新的文档编号。

后续更新记录时必须同时匹配文档编号和 `status = uploading`，并检查实际更新了 1 条。
例如，两段代码同时尝试将同一记录标为成功和失败，只允许其中一次结束操作成功。
这由更新语句和事务实现；表约束只保证字段组合有效，不检查历史状态变化。
不同用户操作不同记录；接收文件期间不持有数据库事务。
这些设计减少并发冲突，是否支持 10 用户同时使用仍须完整接口压测，不能仅凭建表宣称通过。

用户身份、解析任务、批次进度和文档版本不加入本表，随对应功能分别设计。
进程中断留下的 `uploading` 记录如何恢复，继续保留为待评审范围。

## ORM 与建表方式

按用户要求引入 ORM 和表迁移，使用 SQLAlchemy 定义模型、Alembic 管理结构变更。
首次建表由 Alembic 迁移执行；后续新增字段或修改约束时，新增迁移文件并提交 Git。
开发者或部署流程明确执行迁移，不由健康检查或每次服务启动自动建表。
字段约束必须同时体现在 ORM 模型与实际迁移中，不能只做 Python 层检查。
文件位置、执行方法与分步计划见 [ORM 与表迁移](07-orm-migrations.md)。

## 建表后的验证范围

- 合法的接收中、成功、失败记录能保存；成功记录缺少大小或校验和时被拒绝。
- 非法状态、负数大小、错误校验和、结束时间早于开始时间被拒绝。
- 重复文档编号或重复正式存储位置被拒绝；相同文件名和 SHA-256 的不同上传能分别保存。
- 使用真实 PG 验证约束及事务回滚，验证数据不作为正式上传记录保留。

依据：[PG 约束说明](https://www.postgresql.org/docs/18/ddl-constraints.html)、
[PG 时间类型说明](https://www.postgresql.org/docs/18/datatype-datetime.html)。
