# 上传记录保存到 PostgreSQL

状态：本文件记录的内容、状态和保存顺序已评审通过；[PG 接入](04-postgresql-connection.md) 已完成连接验证。
上传表设计与 ORM 接入已评审通过；记录读写已实现（`src/db/upload_records.py`），本地文件保存尚未实现。

## 本地文件和数据库各存什么

本地保存 PDF 的原始字节；PostgreSQL 保存“谁上传了什么文件、文件放在哪里、是否上传完成”的记录。
本步先定义文件和上传结果；用户认证与归属字段随认证方案另行设计，不能接受任意填写的用户编号作为可信身份。
记录用于后续按文档编号找文件、显示上传列表和提交解析，不只是打印一条日志。
本轮不重复写 `metadata.json`；未来 Stage 产物的 manifest 是另一件事，不因此取消。

## 建议保存的内容

| 内容 | 用途 |
| --- | --- |
| 文档编号 | 本次接入的新文档编号，与接口返回值一致 |
| 原文件名、来源格式 | 展示上传的文件；当前格式为 PDF |
| 文件大小、SHA-256 | 核对文件完整性；上传完成前未知的值留空 |
| 存储类型、存储键 | 类型为 local，键为相对路径；以后可以换为存储桶中的对象键 |
| 上传状态 | uploading（接收中）、uploaded（已保存）、failed（上传失败） |
| 创建时间、完成时间 | 记录何时开始、何时完成，失败也记录结束时间 |
| 失败原因 | 保存可排查的原因；不向客户端泄露服务器路径或数据库凭据 |

这些是上传记录，不把解析的 queued/running/succeeded 等状态放进上传状态。
上传成功后解析仍可能失败；解析失败不能把已上传的原文件改成“上传失败”。
数据库驱动使用 Psycopg；表名、字段类型、约束和建表方式见已通过的 [上传记录表设计](06-upload-table.md)。
SQLAlchemy + Alembic 接入设计已通过，详见 [说明](07-orm-migrations.md)；当前已实现 [ORM 基础](08-orm-foundation.md)。

## 建议保存顺序

1. 分配文档编号，用一个短数据库事务创建 uploading 记录，然后结束事务。
2. 分段接收文件，写入本地临时目录，同时计算大小和 SHA-256。
3. 初步检查通过且文件写入完成后，发布到该文档的正式目录。
4. 用另一个短事务补齐记录，并将状态更新为 uploaded。
5. 数据库提交成功后，接口返回 HTTP 201；后续解析只读取 uploaded 的记录。

上传期间不一直占用数据库事务；写文件和写 PG 无法自动成为同一个原子操作。
文件写入失败时清理本次临时文件，并尽量将记录标为 failed。
文件已保存但 PG 更新失败时，返回服务错误，不能返回 uploaded；通过文档编号保留排查线索。
进程退出或数据库断开可能留下 uploading 记录和孤立文件，需要核对后恢复或清理。
这类异常的自动恢复策略仍待评审，不能把请求内清理描述为能覆盖所有中断。

## 验证要求

- 正常上传：PG 有 uploaded 记录，记录对应的文件存在，大小与 SHA-256 一致。
- 同名文件重复上传：编号不同，文件和记录均不覆盖。
- 文件校验或写入失败：没有可供解析的 uploaded 记录。
- 数据库创建或更新失败：HTTP 不报告上传成功，保留可识别的未完成状态或排查线索。
- PG 持久化与事务行为使用真实 PostgreSQL 验证，不能只用内存模拟。

这一步按“PG 接入 → 上传记录 → 文件保存 → 接口串联”逐段实现和评审，不一次写完。
