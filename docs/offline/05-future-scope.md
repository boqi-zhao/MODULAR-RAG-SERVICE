# 后续范围：按需评审

下面是合并后的规划，尚未实现。已确认：PostgreSQL 状态库、每个 Stage 版本产物、至少 10 用户目标。
其他策略、字段、组件和接口不因出现在本页就获得开发授权；MVP 默认参考旧项目，效果不足再单独调优。

## 阶段和依赖

| 阶段 | 建议输入 → 输出 |
| --- | --- |
| chunk | 固定 parse → 块集合、顺序/证据范围、图片引用 |
| refine / enrich（可选） | 固定块表示 → 清理/增强表示、变更与模型请求/响应 |
| image_register | parse 图片 → 资产清单、内容摘要、引用映射 |
| caption（可选） | 块表示 + 图片资产 → 描述、模型请求/响应、合成映射 |
| dense_encode / sparse_encode | 同一固定语料 → 向量 / 词项、频次、长度 |
| vector_write / bm25_build | 编码产物 + 语料 → 独立向量空间 / BM25 快照 |

主链建议 `parse → chunk → [refine] → [enrich] → [caption]`；图片注册从 parse 分支，在 caption 汇合。
最终表示汇总为语料，再分成 dense/vector 与 sparse/BM25 两支。关闭可选阶段直接绑定前一产物，不造伪执行。
refine/enrich/caption 原草案只改表示，不增删块/改父子/证据范围；若需要重分块，另建块集合并评审职责。
caption 与基础文字分开保存，每次读 caption 前的固定表示，防止重跑重复追加。

chunk 等解析评审/验收后讨论，长度、重叠、分隔符、图片关联和父子检索尚未确定。
原 B 方案依赖文字块/坐标，与当前 MVP 不兼容，已归入 [分块历史草案](../history/offline/03-chunk-proposal.md)。
来源偏移草案采用明确文本流上的 Unicode 字符左闭右开区间；不能靠首次字符串匹配猜重复段落位置。
每块保留文档版本、parse 产物及全部证据引用；增强不覆盖原始证据，更换解析器后不能直接比较偏移。
跨解析器标注映射和页面精准定位需要另行设计，当前 MVP 不具备这些能力。

## 语料和索引

语料快照固定有序文档版本、块集合/表示、检索 chunk_id 和输入摘要；默认每文档一个版本，空语料拒绝建索引。
Dense/Sparse 要覆盖同一完整块清单与**文字版本摘要**；仅 ID 相同不能组合，不能静默丢弃失败块。
每次构建独立命名空间和 BM25 位置；后端记录沿用 chunk_id，新分块不会残留旧块。
BM25 原建议从完整固定语料重建；N 是检索块数、DF 是含词项的块数，平均长度基于同一清单。
sparse 保存逐块统计，bm25_build 才计算全语料统计/打分参数。

组合 manifest 固定语料、两侧 artifact_id、命名空间、后端版本和校验；核对向量维度/稀疏参数，两支完整成功并兼容才 building → ready。
只成功一支就保留该产物、组合 failed；恢复显式复用成功不可变分支，失败分支用新空间。
单次 vector_write 内部批次重试沿用候选空间/块 ID，最终检查全清单/数量/摘要；失败外部写入不可查询。
ready 来源不修改，损坏在状态库记 unavailable；ready 不等于已发布到在线服务，单侧索引另行设计。
验收包含：100 块改成 80 块无残留、caption 重跑不重复、两侧 ID 同但文字异时拒绝组合。

## 多用户、额度和进度

10 个独立用户会话是目标，不能等同于 10 个 worker 或 10 条数据库连接；尚无完整流程实测结果。
分别配置全服务活跃文档数、各 Stage 执行数、模型并发/每分钟配额及单用户/批次上限。
原建议文档内部并发可设 1/3，其余持久排队；多个进程不能各算一份全局额度。
先拿额度再领取，等额度仍 queued；退避/语料屏障等待释放文档额度，语料执行只占对应 Stage 额度，避免互相堵塞。
额度与租约/token 在 PG 短事务协调；接管不阻止失联旧进程继续消耗资源，应记录这种风险。
按用户轮转、用户内按批次/文档排序，空闲时可借额度；有其他用户排队限制继续领取，不抢占已运行 Stage。
API/worker/恢复池有界、总连接数匹配 PG 预算；耗时任务不阻塞 API，上传避免整批读入内存。

批次冻结拥有者、文档项、计划和配置；每个 batch_item_id 绑定版本，重试不改变 total，追加文件建新批次。
上传失败项不静默纳入处理清单；一个 CSV 文件未来也仍是一个文档项，记录数不改变 total。
身份认证另行设计，不能信任请求自填 user_id；状态/产物/进度/重跑和复用都要检查归属。

进度建议持久化 `total / succeeded / failed / pending / running / revision`，completed = succeeded + failed。
项全部文档级节点完成才成功；尚有自动重试不计最终失败，阶段完成/重试不能重复增加计数。
“文档 100/100，索引构建中”时整个 run 仍 running；必要语料/索引节点完成、产物可用才整批成功。
有文档最终失败默认整批 failed；选择成功子集继续时显式建新语料/计划，不抹去原失败。
恢复终止项时计数可回退、revision 增加，历史事件保留；不能承诺跨恢复轮次 completed 单调。

SSE 是进度推送建议，保留状态查询；重连发最新持久化快照，客户端忽略旧 revision，不保证回放全部事件。
断开不取消任务，终态仍可查询；不长期占 PG 连接，慢客户端有界缓冲/合并快照，变化推送与心跳分开。
10 用户验收用不同身份和独立批次、开始屏障形成重叠，持续观察到终态；并发 1/3 各跑正常场景。
另测大小批次公平性、SSE 重连、损坏 PDF/模型错误、worker 接管和用户隔离；模拟阶段不能替代真实完整流程。
报告固定输入 hash/大小/页数/类型、硬件/模型/配置，测提交/进度延迟、排队/完成时间、资源与池等待。
典型规模、时限、硬件和模型配额待冻结；超时与最终状态都要记录，不以无限等待或拒绝部分用户算通过。

## 组件和格式边界

PostgreSQL 已选：支持任务状态/并发协调，代价是部署、连接池、迁移与备份；10 用户本身不证明 SQLite 不够用，也不意味着向量库必选 pgvector。
任务表 + 独立 worker 待评审；Redis/Kafka 尚未选，不为组件数量提前引入。
Redis 仅在共享限流/查询热点有证据后讨论；PG 仍权威，缓存回源与模型限流保守降级分别设计。
Kafka 仅在独立消费者、历史重放或现有分发不足时讨论；若用 outbox，状态与待发事件同事务、消费者持久去重。
Kafka 事务不覆盖外部文件/索引，事件重放不自动等于业务强制执行。

当前单机本地文件；多机再评审 OSS/S3，唯一版本键、上传后校验、PG 引用提交和孤立对象回收，不能套目录 rename。
备份/恢复包含数据库和全部被引用字节，恢复后校验；保留、导出、配额、清理策略尚待评审。
Markdown/QA CSV 后续接入：格式识别和策略选择分开，统一契约与格式元数据分开，不强制所有格式有 PDF 页码。
Markdown 保留标题/列表/代码及来源；CSV 保留问答配对、记录/字段定位，物理行号不直接作为记录身份。
编码、列映射、缺失/重复值、超长 QA、图片能力和是否逐条导入另行评审；当前不编写空解析器冒充支持。

技术依据保留：[PG 队列锁](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE)、[SQLite 场景](https://www.sqlite.org/whentouse.html)、[Redis 限流](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)、[Kafka 语义](https://kafka.apache.org/41/design/design/#message-delivery-semantics)、[SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。
