# Redis 与 Kafka 的启用条件

状态：设计或用例建议；具体批准范围见对应评审入口。

## 4. Redis：缓存与限流的候选

实际问题目前尚未出现：状态查询是否形成数据库压力？多个 worker 是否共用有限的模型请求额度？
这些问题应通过查询延迟、数据库负载、模型 429 响应及并发调用记录确认。

**当前建议：暂不引入 Redis，保留明确的启用条件。**
当多个执行进程需要共享模型调用额度时，可评审 Redis 原子限流；官方提供多种限流实现思路。
依据：[Redis 限流文档](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)。
若状态查询成为热点，可缓存短期状态，但 PostgreSQL 仍是权威记录；终态和产物版本不能凭缓存判定成功。
缓存设计需说明键、TTL、失效时机、可接受陈旧程度，以及 Redis 不可用时的行为。
模型限流失效时建议暂停或保守降低调用额度；状态查询缓存失效时可回源数据库，两种降级分开设计。
初期单 worker 可用进程内并发限制；这不等同于跨进程限流，扩展 worker 时必须重新评审。
执行租约优先由状态库统一维护，避免同时维护数据库和 Redis 两套执行所有权。

## 5. Kafka：事件需求明确后再评审

实际问题：若构建完成事件需同时被评测、审计等独立系统消费，且要保留历史并重放，事件流可能有价值。
目前三个大阶段只是设计边界，尚无多个独立消费者的实现，也没有消息吞吐量基线。

**当前建议：暂不引入 Kafka。**
引入条件是出现独立订阅者、历史事件重放需求，或经测量确认现有分发机制不满足需求。
如果只是需要任务重试、延迟执行与失败队列，应同时比较成熟任务队列方案，而非直接把 Kafka 当定时调度器。
Kafka 与 PostgreSQL/产物文件之间没有自动的一次性提交保证；Kafka 内部事务不覆盖任意外部写入。
依据：[Kafka 消息交付语义](https://kafka.apache.org/41/design/design/#message-delivery-semantics)。
若以后选 Kafka，先设计 transactional outbox：业务状态与待发送事件写入同一数据库事务。
独立发布器发送后登记结果；发送成功但登记失败仍可能重复发送，消费者按 event_id 持久化去重。
事件带 schema_version 和固定产物引用；“重放通知”不隐式等于“强制重跑业务阶段”。
消费位点、处理完成、租约过期与外部副作用分别处理，不宣称整个 RAG 流水线 exactly-once。
