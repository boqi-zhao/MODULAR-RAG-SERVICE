# 状态库与并发对比

状态：设计或用例建议；具体批准范围见对应评审入口。

## 2. 状态存储：SQLite 与 PostgreSQL

实际问题：任务、执行尝试、版本引用必须持久化；多个 worker 竞争任务时不能互相覆盖状态。
进程重启后还需识别未完成任务、旧租约与已提交产物，内存字典不能承担这些职责。

| 方案 | 适用场景 | 主要代价与边界 |
| --- | --- | --- |
| SQLite | 单机开发、轻量部署、学习基础状态模型 | 部署简单；同一数据库同时只有一个写入者，需要控制写事务长度 |
| PostgreSQL | 独立 API/worker、并发领取任务、学习事务与服务部署 | 需维护数据库服务、连接池、迁移、备份及集成测试环境 |

SQLite 的写并发限制不等于“不适合生产”，是否合适取决于写入竞争与部署方式。
官方也建议在多机直接访问或大量并发写入等条件下考虑客户端/服务器数据库。
依据：[SQLite 使用场景](https://www.sqlite.org/whentouse.html)。

**已确认：采用 PostgreSQL 作为主要状态库。**
理由是多用户提交、多 worker 调度和状态查询需要协调，并希望实作事务、并发和恢复机制。
10 用户本身不足以证明 SQLite 性能不够；不实现 SQLite 后端，保留比较作为选型依据。
表结构、Python 数据库库、迁移工具和数据库版本在实现对应模块时确定。
状态库存任务与引用元数据；原始文件、图片和大批量向量不默认全部塞进状态表。
采用 PostgreSQL 也不自动意味着向量索引采用 pgvector，两个职责分开评审。

### 2.1 并发能力对比

| 并发行为 | SQLite | PostgreSQL | 项目设计影响 |
| --- | --- | --- | --- |
| 读取与写入 | WAL 模式允许读写重叠，同一数据库仍只有一个写入者 | MVCC 提供快照读取，通常读写互不阻塞 | 查询进度与 worker 写入可重叠，但仍需控制事务 |
| 多个写入者 | 写事务排队，短事务时仍可服务多个用户 | 可并发修改不同记录，冲突记录可能等待行锁 | 按任务记录领取，不持有全局业务锁执行长任务 |
| 多消费者领取 | 没有 PostgreSQL 的行锁领取机制，需另定原子领取方案 | 可使用行锁与 SKIP LOCKED | 分开处理领取、租约、重试与公平调度 |
| 流水线能力 | 数据库能力不决定 PDF/模型吞吐量 | 数据库能力同样不保证 10 用户端到端完成 | 用真实 PDF 验证上传、调度、进度和完整产物 |

行为依据：[SQLite WAL](https://www.sqlite.org/wal.html)、[PostgreSQL MVCC](https://www.postgresql.org/docs/18/mvcc-intro.html)。
选型不附带未经实测的倍数结论；测试重点是本服务的多用户体验及正确性，不为此额外实现 SQLite 流水线。
