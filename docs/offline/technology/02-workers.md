# 数据库任务领取与 worker

状态：设计或用例建议；具体批准范围见对应评审入口。

## 3. 执行解耦：先评审数据库任务队列

实际问题：解析、编码耗时较长，HTTP 提交不能等待整个流水线完成；worker 崩溃后任务需要可恢复。
“独立 worker”表示执行进程独立于 API；不要求初期为每个 Stage 部署一个微服务。

| 方案 | 可以解决什么 | 需要自己负责什么 |
| --- | --- | --- |
| HTTP 内直接执行 | 调用路径简单，适合调试短阶段 | 请求超时、进程重启与长任务恢复；不建议作主执行路径 |
| 数据库任务表 + worker | 持久化提交，API/worker 分离，与状态更新共享数据库事务 | 领取、轮询、租约、重试、退避、并发限制和清理 |
| 成熟任务队列 + broker | 使用现成分发与 worker 机制 | 消息与数据库一致性、业务幂等、运行维护及框架约束 |
| Kafka 事件流 | 持久事件、多订阅者、事件重放 | 分区设计、消费位点、积压、重试调度及外部写入一致性 |

**当前建议：使用 PostgreSQL 任务表与独立 worker，暂不增加 broker。**
这能集中验证现有设计最重要的状态机与恢复语义；数据库队列本身仍需要认真实现。
多 worker 领取可使用短事务中的 `FOR UPDATE SKIP LOCKED`，同时登记所有者、租约及递增 token。
官方将 SKIP LOCKED 列为队列式多消费者减少锁竞争的用途；它不提供公平调度或完整任务系统。
依据：[PostgreSQL SELECT 锁定说明](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE)。
领取后立即结束事务，再执行耗时逻辑；心跳与结果提交通过条件更新检查当前所有者和 token。
任务超时后旧 worker 可能仍在运行，所以租约提供执行所有权控制，不保证昂贵计算只发生一次。
对外模型调用可能重复计费；产物提交和索引写入仍需遵循不可变版本与幂等规则。
持久化错误类别、attempt 次数、next_attempt_at，避免失败任务被紧密循环领取。
依赖满足后，在同一状态库事务中登记可运行后继；定期对账补齐漏调度节点。
任务表只派发 Stage，实际依赖与重跑决策仍由 Runner 负责。
