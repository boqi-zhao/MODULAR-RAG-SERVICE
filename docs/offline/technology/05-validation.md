# 工程验证与选型顺序

状态：设计或用例建议；具体批准范围见对应评审入口。

## 7. 工程深度如何证明

每项能力都应留下实现、测试/演练和结果记录；设计文档只能说明意图。
面试材料区分“已实现”“已验证”“后续方案”，演示规模和结果按实测报告，不虚构生产规模。

| 工程能力 | 建议演练或测试 | 可讨论的取舍 |
| --- | --- | --- |
| 并发领取 | 两个 worker 同时竞争可运行任务 | 短事务、行锁、轮询成本、任务公平性 |
| 失败恢复 | 计算中杀掉 worker，租约过期后恢复 | 重复计算与只允许当前所有者提交的区别 |
| 防止旧执行提交 | 暂停旧 worker，接管后让旧 worker 恢复 | fencing token 与副作用边界 |
| 输入可复现 | 更改上游最新版后恢复旧任务 | 固定版本读取与复用指纹 |
| 产物一致性 | 发布文件后、登记数据库前故障注入 | 跨资源提交窗口与对账恢复 |
| 索引隔离 | 换分块方案重建并核对完整 ID 清单 | 新空间的存储成本与旧块污染风险 |
| 数据库迁移 | 从前一 schema 升级并读取已有任务 | 兼容策略、失败处理和回滚限制 |
| 运维可见性 | 制造失败和积压并查看记录 | 错误分类、日志关联与指标含义 |

第一批可观测性先保存结构化日志，关联 run_id、execution_id、stage 和 artifact_id。
记录排队等待、执行耗时、成功/失败数、重试次数和待执行数量；明确统计时间窗和计数单位。
模型接入后记录限流响应、调用耗时及可获得的使用量，避免用总耗时掩盖外部调用瓶颈。
监控平台、分布式追踪和告警系统按具体观察需求再选，首先保证数据可采集、可解释。

## 8. 建议推进顺序

1. 评审身份规则、Stage 粒度和 manifest；这是所有存储与执行组件的前提。
2. 基于已选 PostgreSQL 设计状态表、迁移与连接预算；不再并行开发 SQLite 后端。
3. 用内部样例验证契约后实现文件产物与 PDF parse/chunk，再接入状态库、独立 worker 和最小 API。
4. 用至少 10 用户、内部文档并发 1/3、故障注入与重启恢复验证，再形成本地部署说明。
5. 接入模型和隔离索引，测量后判断限流、缓存、外部任务队列是否值得引入。
6. 在线与评测阶段独立设计；若出现事件订阅/重放需求，再评审 Kafka 与 outbox。

PostgreSQL 的选择已确认；数据库依赖和部署配置随对应模块开发添加，届时锁定版本并记录验证步骤。
Redis、Kafka 和索引后端仍未确定；不能把状态库的确认扩大为全部业务实现授权。
