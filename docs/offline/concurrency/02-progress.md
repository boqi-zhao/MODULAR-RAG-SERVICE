# 批次进度与推送

状态：设计或用例建议；具体批准范围见对应评审入口。

## 3. 进度口径

每个批次保存 total、succeeded、failed、pending、running，以及进度修订号 revision。
completed = succeeded + failed；失败只在该项计划终止、无待执行自动重试时计入。
对外展示“已处理 x/100，成功 s，失败 f”；不能把失败项展示为成功文档。
同一文档项内的阶段完成与重试不重复增加 completed；计数由项状态转移驱动。
分配与计数在 PostgreSQL 事务中一致更新，或查询同一一致快照聚合，不能用 worker 内存累计。
阶段执行中展示具体阶段与可获得的阶段进度；成功计数仅在该项所有文档级阶段完成后增加。
输入产物复用可使项直接完成，但仍只计一次，并记录复用来源。

### 3.1 文档完成与整批完成

批次计划必须声明哪些节点属于文档级，哪些属于语料/索引级。
文档级处理完成不等于索引已经可检索；完整流程还可能包含语料汇总与索引构建屏障。
当语料阶段需要完整块清单时，先等待各文档对应的前置阶段完成，再冻结语料快照。
编码阶段可按固定语料清单拆分调度，但总产物校验必须覆盖完整清单，不能只检查局部分片。
若编码被定义为语料级，另报其进度；若细分为文档级节点，项完成也必须等待这些节点成功。
例如“文档处理 100/100，正在构建索引”是合法中间状态，整个 run 仍为 running。
整批成功要求计划内所有必要节点成功、完整产物可用，以及启用索引时 index snapshot 为 ready。
部分文档失败时保留成功产物，默认整批 failed，索引不跳过失败项后宣称成功。
用户选择以成功子集继续时应明确创建新语料/计划，保持原批次的失败事实可追溯。
失败恢复会创建新尝试；若恢复已终止的文档项，其失败计数可回退，revision 增加并标示恢复中。
同一轮执行的计数递增，跨恢复轮次不承诺 completed 单调；历史状态变更保留。

## 4. 进度推送建议

首批建议提供 SSE 单向进度流，同时保留普通状态查询接口作为恢复与脚本验证入口。
SSE 的事件格式和重连机制依据 [MDN 文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。
事件包含 run_id、revision、上述计数、批次状态和语料/索引阶段；事件 ID 可使用批次 revision。
连接建立或重连时发送最新持久化快照，客户端忽略旧 revision；首批不承诺回放所有中间事件。
断开推送连接不取消后台任务；重新订阅后仍读取同一批次，终态即使错过事件也可查询。
SSE 不长期占用数据库连接或事务，读取后释放连接；初期可通过短周期查询获取变化。
相同状态不重复推送，独立发送心跳；慢客户端使用有界缓冲并合并中间快照，保证能获取终态。
没有 Redis Pub/Sub 或 Kafka 也可以提供进度流，增加事件分发组件需有实测需求。
