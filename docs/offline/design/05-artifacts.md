# 产物与提交协议

2026-10-07 用户已明确每个小 Stage 必须独立落盘、可追溯、可复用；以下具体存储格式和提交协议仍待评审。

## 4. 产物格式与持久化

建议运行数据根目录位于 Git 忽略的 `data/`，通过配置指定，不使用旧项目的数据目录。
按 artifacts/<artifact_id>/ 保存每个成功产物，临时结果位于独立 staging/<execution_id>/。
原始文档与图片字节进入内容寻址的 blobs/；执行状态及产物引用元数据进入状态库。
初期 API/worker 共享单机数据卷；多机产物访问与对象存储提交协议需另行设计。
产物保留上游引用与输入清单；被引用的字节和上游快照不得删除，完整输入通过这些引用可重建。
模型阶段另存实际发送的完整业务请求、响应与逐项错误；认证头、密钥不属于产物内容。
不强制复制大文件或全部祖先输出；脱离存储迁移时需要导出完整引用闭包。

### 4.1 manifest 字段

| 字段组 | 必需内容 |
| --- | --- |
| 身份 | manifest_schema_version、artifact_id、stage、stage_contract_version、execution_id、run_id、用户归属；文档级产物另含 batch_item_id |
| 来源 | 文档/语料版本、具名上游 artifact_id、输入文件/记录摘要及读取范围 |
| 实现 | 实现版本、源代码摘要、依赖锁文件摘要、执行环境摘要 |
| 配置 | 完整有效配置、配置摘要、模型实际版本、Prompt 正文/版本、随机种子 |
| 输出 | 文件相对路径、类型、大小、SHA-256、记录数、输出 schema 版本 |
| 执行 | 开始/结束时间、耗时、最终结果、警告、校验摘要、执行指纹 |
| 能力 | 是否允许复用、复现限制、外部资源引用与版本 |

建议结构化清单用 JSON，逐块记录用 JSONL，大型向量或图片用独立二进制文件并列入清单。
每个阶段定义其输出 schema，不把任意目录结构作为成功契约；文件路径不能逃逸产物目录。
执行中状态写入状态库；成功 manifest 只在完成时生成，之后不再更新。
失败尝试也保存输入引用、已产生输出、日志及 failure manifest，但放在 attempts/ 下，仅供诊断。
日志和诊断可被查看，失败候选始终不允许作为正常阶段上游。

### 4.2 保存与提交顺序

1. 状态库创建执行尝试，保存已经解析的输入引用、计划及候选产物 ID。
2. worker 取得带期限的执行租约，写入独立 staging 目录及周期性进度记录。
3. Stage 完成输出；ArtifactStore 校验 schema、引用、清单完整性及所有文件校验和。
4. 写入成功 manifest；在短状态库写事务内锁定对应执行记录、复核租约与 fencing token，再在同一文件系统内原子重命名目录。
5. 同一事务登记已发布产物，并把执行标记为 succeeded；下游由此读取，刷新策略按持久性要求实现。

文件与状态库不共享事务：启动恢复扫描已发布但未登记的产物，校验原尝试及 fencing token 后补登记。
恢复、领取、续租和提交使用 PostgreSQL 中同一任务所有权记录的并发控制协议；具体 SQL 在实现时定义。
过期尝试的孤立目录仅保留为诊断，不能补登记为成功；提交短事务内禁止模型调用或大文件写入。
只有数据库成功但文件丢失/损坏时标记产物不可用并阻断下游，不能自动改用其他版本。
租约带递增 fencing token；过期 worker 的完成操作必须被拒绝，防止恢复后两次提交。
失联尝试先标记 interrupted，由恢复逻辑处理；心跳超时不直接推断业务阶段永久失败。
对外索引写入不受目录重命名保护，采用独立命名空间和提交标记，详见索引规则。
初期不自动清理产物；后续垃圾回收必须检查引用闭包、活动任务与保留策略。
