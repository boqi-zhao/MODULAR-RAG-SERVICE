# 分步开发与讲解流程

状态：2026-10-06 按用户要求取消 TDD；原解析代码与测试已删除，准备根据已确认文档分步重写。
原用例保留为需求和验收依据，不要求先写失败测试。

## 每一步怎么做

1. 根据文档选一个小范围，用通俗语言说明目的、输入输出和数据处理过程。
2. 说明本步会修改哪些文件、暂时还有哪些能力没做，用户明确指示开始后再编码。
3. 只实现本步范围，不顺手完成后续模块；未确认的字段和业务规则先讨论。
4. 使用真实样本检查本步结果，按实际风险补充自动测试，运行 Ruff 检查。
5. 结合代码位置解释关键逻辑，展示如何调用以及实际结果。
6. 等用户理解本步并决定下一步，再继续。

需求评审通过不自动触发编码，也不代表全部业务已获开发授权。
用户要能理解代码并讲清实现思路；完成一个大模块不能替代逐步讲解。

## 每步编码前检查分工

后续接口按“请求 → router → service → 文件保存/数据库读写”的顺序组织。
router 负责 HTTP 接入与响应，service 负责业务流程；service 应能脱离 FastAPI 独立调用。
结构化输入、输出使用 Pydantic 模型，放在功能目录的 `schemas.py`；路由声明 `response_model`。
例如上传的成功结果必须包含文档编号、大小和 SHA-256，失败结果必须包含原因，由模型检查是否齐全。
文件流和数据库 Session 不强制改成 Pydantic 模型；详细约定统一见 [AGENTS.md](../../AGENTS.md#routerservice-与数据模型规范)。

## 验证要求

- 取消 TDD 只是取消“先写失败测试”的顺序要求，仍要核对实现是否满足已确认行为。
- 按需要选择样本检查、单元测试、集成测试和完整流程验证，避免无实际用途的测试。
- 需求变化影响已确认行为时，先更新文档并重新确认。
- PostgreSQL 锁与并发行为用真实 PostgreSQL 验证，模拟测试不能代替真实组件验收。
- 10 用户验收与内部文档处理并发分开，见 [并发设计](04-concurrency.md)。
- 当前仅计划实现 PDF；Markdown/QA CSV 保留扩展边界，后续单独讨论。
- 每个 Stage 必须先明确独立产物的保存、版本追溯与读回契约；纯计算子步骤完成不等于 Stage 完整交付。
- Stage 验收包含新进程读回、固定上游复用、换策略后新旧结果共存及损坏拒绝复用，详见 [项目约定](../../AGENTS.md#每个-stage-的产物与调优约束)。
- 每次代码写入不超过 100 行，每 10–15 行代码添加说明性注释。
- 没有自动测试时明确说明，不能把“未收集到测试”写成“测试通过”。
