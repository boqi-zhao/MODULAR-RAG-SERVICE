## 1. 要解决的问题

当前 PDF 需求包含文字、图片、页序与原始矩形，以及扫描风险和部分失败诊断。
每个 Stage 的产物要落盘、可追溯、可复用；以后换解析策略时，从 parse 重跑下游并保留历史实验。
选择解析库时既要考虑文本效果，也要考虑输出能否直接满足这些定位要求。

源码核对补充见 [历史摘要的源码核对](../history/offline/01-pdf-history.md#既有项目源码核对)。

MarkItDown 默认 PDF 转换结果主要是 Markdown，没有直接返回本项目要求的逐文字块页序/矩形。
这不代表 PDF 没有坐标，也不代表其底层无法提取布局；它意味着直接使用该转换接口仍需补定位输出。
依据：[本次查看的官方 PDF 转换器](https://github.com/microsoft/markitdown/blob/main/packages/markitdown/src/markitdown/converters/_pdf_converter.py)。
这里的官方 main 源码是选型依据，不等于旧项目所安装依赖的版本；现已安装并锁定 PyMuPDF 1.28.2。

## 3. 候选方案与取舍

| 方案 | 优点 | 需要处理的代价与限制 |
| --- | --- | --- |
| MarkItDown 文本 + PyMuPDF 图片 | 沿用既有业务策略，可作为后续对照基线 | 文字块坐标需另做提取及对应，不能直接把另一引擎坐标套到 Markdown 上 |
| PyMuPDF 统一图文 | 可直接取得文本块与矩形，图文来自同一解析引擎，减少对应关系工作 | 文本效果仍需真实样本检查；复杂阅读顺序、OCR 与结构化表格不因此自动解决 |

PyMuPDF 的 blocks 输出带文字与矩形，dict 输出提供图文结构；依据 [官方文本提取说明](https://pymupdf.readthedocs.io/en/latest/app1.html)。
“定位适配工作更少”是接口与工程取舍判断；“文本质量更好”目前没有实验依据。

## 4. 决策经过与当前结论

1. 前期设计选择 PyMuPDF，并通过了原始位置、图片与扫描风险等首批行为要求。
2. 用户要求以旧项目为业务基线，曾决定先沿用 MarkItDown + PyMuPDF，以后按效果调整。
3. 明确默认 MarkItDown 输出不直接满足文字块坐标要求后，用户重新确认：先用 PyMuPDF 统一处理，效果不好再调优。

当前采用 PyMuPDF；旧组合保留为可比较的候选，不是当前正在实现的默认策略。
这是用户明确确认的选型调整；不声称已证明旧策略效果差，整套计算设计现已通过，但完整实现尚未交付。
之后的策略调整仍要记录问题、对比依据和用户决定；阶段职责与版本复用规则保持明确。
