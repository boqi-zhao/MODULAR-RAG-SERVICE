# 每次选型或调优怎么记录

要求来源：2026-10-07 用户要求集中、独立、详细记录，保留可用于面试讲述的依据。
单个文件只记录一次决策或一次实验，控制在 200 行以内；字段可以按主题调整。

## 1. 记录基本信息

- 编号、日期、类型：技术选型 / 策略调整 / 调优实验。
- 对应任务与 Stage、相关设计、基线或上一条记录。
- 分别说明：建议、用户确认、开始实现、验证结果、代码评审、提交/推送。

## 2. 说明为什么需要做

- 遇到的需求或实际问题，目标是什么，怎样判断是否达到目标。
- 原方案怎么做，有什么可验证的不足；没有效果数据就明确说明。
- 候选方案各自满足什么、缺什么，选择理由与付出的成本。
- 最终用户决定、接受的局限，以及什么情况会重新考虑。

## 3. 留下调优实验依据

- 固定输入、样本/评测集清单与版本或摘要，实验与产物引用。
- 基线和候选的策略、有效参数、实现/依赖/模型/Prompt 版本；不适用的项目注明。
- 机器或服务运行条件、复现命令、指标定义、重复次数和公平比较条件。
- 前后实际结果及原始报告位置，正确性、质量、耗时与资源开销按需要分别记录。
- 无提升、失败、误判或数据缺失也如实保留；未测量的项不得填猜测数字。
- 阶段回归和 RAG 业务效果分别说明，不能用“解析测试通过”替代“检索效果提升”。

## 4. 写清结论与贡献边界

- 结论：采用、暂缓、否决或仍需验证；与前面的证据对应。
- 哪些来自开源实现，哪些是自己设计/实现，哪些只在本机样本或模拟环境验证。
- 当前限制和后续实验方向；后来改变决定时新建记录并链接本条。

## 5. 准备面试讲述

用一小段话回答：问题是什么 → 比较了哪些方案 → 为什么选择 → 做了什么 → 如何验证 → 有什么局限。
尚未实现的选型只能讲“为何选择与准备如何验证”；实际验证后再补成果与数字。
面试讲述必须能回到本条的源码、提交、版本产物或报告，不把计划包装成实际贡献。
